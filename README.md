# uno-mini-os
中文：
在智能化技术飞速普及的今天，操作系统早已成为电子设备的核心灵魂。从计算机端的 Windows、Linux 系统，到移动终端的安卓、iOS 系统，再到嵌入式设备搭载的各类实时操作系统，各式各样的系统支撑着整个数字世界的有序运行。长久以来，操作系统被普遍认定为高精尖技术的产物，是专业工程师与科研人员的专属研究领域，普通技术爱好者难以触及系统底层的设计与开发。直到 Arduino UNO 开发板进入嵌入式爱好者的视野，基于该硬件平台逐层搭建、迭代、优化，一套轻量化嵌入式微型操作系统 UNO Mini OS 得以诞生。这套系统充分验证，硬件资源有限的单片机平台，同样可以承载图形交互系统，方寸芯片之间，亦可构筑属于硬件项目的数字星河。

UNO Mini OS，是一套基于 Arduino UNO 主控板，搭配 TFT 彩色显示屏、ESP32 蓝牙与 WiFi 模块、MAX3421 USB Host 扩展板等外设硬件，依托底层代码逐层搭建功能、经过大量调试优化形成的轻量化嵌入式微型操作系统。这套系统没有商业操作系统庞大臃肿的后台进程，不搭载复杂的内核调度模块，却在仅 2KB 静态内存、32KB 闪存的极限硬件条件下，实现图形界面交互、鼠标操控、蓝牙通信、网络浏览、外设拓展、多功能应用集成等一系列核心能力。该项目不只是一次嵌入式技术实践，更是对低端单片机性能边界的探索，是嵌入式工程思想落地的完整载体，具备极高的实践价值与参考意义。

初识 Arduino UNO，是嵌入式科创领域入门实践的常见起点。这款搭载 ATmega328P 单片机的开源开发板，凭借极简的操作逻辑、开源的代码生态、灵活的硬件拓展能力，成为无数嵌入式爱好者开展基础实验的通用硬件平台。在大众认知当中，Arduino UNO 大多用于简单的灯光控制、传感器检测、电机驱动等基础验证实验，是新手学习编程逻辑与硬件交互原理的工具，几乎不会有人尝试在这款算力与内存资源受限的单片机上搭建完整的操作系统。绝大多数嵌入式操作系统开发项目，都会优先选择资源更充足的 STM32、ESP32 等高性能主控芯片，主动规避 UNO 内存容量小、运算主频低、硬件资源高度受限的短板。

但探索硬件边界的项目思路，选择直面这份硬件限制。在大量基础实验完成之后，随着单片机编程逻辑、串口通信原理、屏幕驱动机制与硬件交互规则的逐步掌握，一个大胆的构想逐步成型：既然高性能芯片可以承载完整操作系统，那硬件配置极简的 UNO 平台，能否承载一套专属的微型 OS？能否让这块小小的开发板，摆脱 “入门教学玩具” 的标签，成为拥有独立图形界面、可交互、可拓展、集成多项功能的微型计算机系统？带着对硬件极限的探索目标，UNO Mini OS 开发项目正式启动。

项目开发之初，摆在整个工程面前最大的难题，便是硬件资源的极致限制。Arduino UNO 的硬件配置，放在当下的智能设备生态当中，属于资源极度精简的类型：仅有 2KB SRAM 运行内存、32KB FLASH 闪存，16MHz 的运行主频，不存在原生操作系统内核支持，没有缓存优化机制，不具备多线程硬件调度单元。对比动辄 GB 级内存、GHz 级主频的消费级智能设备，UNO 的硬件资源体量渺小到几乎可以忽略不计。传统嵌入式系统开发流程都会主动规避这类短板，而 UNO Mini OS 项目，需要在这样的硬件基础之上，搭建一套拥有图形界面、交互逻辑、多应用模块的操作系统，工程实现的难度可想而知。

为保障系统能够稳定运行，项目摒弃网络上现成的臃肿开源代码模板，全程采用轻量化底层逻辑编写，对每一行代码开展极致优化，剔除冗余语句、精简变量定义、复用内存空间，将有限的硬件资源压榨到合理上限。商业操作系统拥有完善成熟的内存管理机制，而 UNO Mini OS 没有任何原生底层机制加持，项目团队自主设计简易内存调度逻辑，严格限制全局变量数量，采用动态内存复用方案，规避内存溢出、程序卡死、系统闪退等一系列常见故障。为适配 TFT 彩屏显示输出，项目选用 MCUFRIEND_kbv 专用驱动库，自主绘制系统桌面、图标、光标、菜单栏，手动适配屏幕分辨率与色彩显示逻辑，从零搭建起整套图形交互体系。

系统界面搭建，是项目开发过程中第一个攻坚难点。操作系统的核心能力之一，便是可视化交互，没有图形界面，绝大多数上层功能都无法落地实现。项目初期，硬件只能实现简单的单色文字输出，屏幕闪烁、文字重叠、界面卡顿、光标偏移等问题接连出现。由于 UNO 算力资源有限，每一次屏幕刷新、每一个像素点绘制，都会占用大量系统资源，代码逻辑稍有疏漏，就会直接造成程序死机重启。为解决界面卡顿现象，项目反复调试屏幕刷新频率，优化绘图函数逻辑，采用局部刷新替代全屏刷新的方案，只更新屏幕画面发生变动的区域，大幅降低系统算力消耗。与此同时，项目自主设计系统 UI 布局，划分桌面状态栏、应用图标区、功能菜单栏，搭配自定义光标样式，让简易 TFT 屏幕呈现出规整、可操作的可视化操作系统界面，彻底摆脱单片机仅依靠串口调试的枯燥模式，真正实现图形化人机交互。

图形界面框架成型之后，交互方式升级成为项目的核心目标。传统单片机操作高度依赖计算机下发串口指令，无法脱离上位机独立运行，而具备独立交互能力，是微型操作系统的核心特征。为此，项目开启漫长的外设适配与交互逻辑开发工作，先后攻克鼠标操控、蓝牙通信、网络访问、USB 外设拓展四大核心功能模块，让 UNO Mini OS 的实用性与完整性得到大幅提升。

鼠标可视化操控，是 UNO Mini OS 最核心的交互突破点，也是调试周期最长、故障排查最繁琐的功能模块。项目初期采用 ESP32 蓝牙透传方案搭建鼠标数据通路：通过计算机端 Python 脚本捕捉鼠标坐标与按键信号，借助 BLE 蓝牙协议传输至 ESP32 模块，再由 ESP32 通过软串口转发数据至 UNO 主控，最终驱动屏幕光标移动、点击响应。这套三级透传架构逻辑复杂，涉及多设备协同、跨硬件通信、协议解析等多重技术难点。

开发调试阶段，各类软硬件故障接连出现：波特率不匹配造成数据乱码、TX/RX 引脚接反造成通信中断、计算机端 Pygame 图形 GUI 线程与 Bleak 蓝牙库冲突造成程序死机、ESP32 蓝牙服务初始化时序错误造成设备连接失败、多设备通信时序紊乱造成光标漂移卡顿。为解决上述故障，项目逐行排查代码漏洞，统一 ESP32 与 UNO 软串口通信波特率，修正硬件接线逻辑，采用多进程隔离方案规避计算机端线程冲突，优化 ESP32 蓝牙服务启动时序，新增设备扫描、连接、断开状态反馈机制，逐步解决蓝牙通信相关各类 bug。经过上百次调试优化，最终实现计算机鼠标与 UNO 屏幕光标的精准联动，光标移动顺滑、点击动作响应灵敏，真正落地图形化可视化操控。

后续为优化硬件架构、简化设备链路、规避蓝牙通信存在的不稳定性，项目新增 MAX3421 USB Host 扩展板硬件方案。这款扩展板完美适配 Arduino UNO，能够为原生不支持 USB 主机功能的 UNO 拓展 USB 外设能力，可直接接入有线 USB 鼠标、键盘等 HID 人机交互设备。项目重新适配底层驱动代码，优化数据解析逻辑，摒弃繁琐的蓝牙三级透传架构，实现 USB 鼠标直连操控。两套交互方案的迭代优化，让 UNO Mini OS 拥有稳定、高效的人机交互能力，实现脱离计算机独立运行、自主操控的核心目标。

蓝牙多功能通信模块的开发落地，让 UNO Mini OS 从单一交互系统，升级为具备双向通信能力的智能微型系统。在基础鼠标透传功能之上，项目深度优化 ESP32 固件代码，适配老旧版本 NimBLE-Arduino 库 API，修复扫描回调、设备连接、地址解析等多项编译报错，自主开发蓝牙扫描、设备连接、断开连接、状态回传等完整功能。当前版本 UNO Mini OS，可通过自带蓝牙应用，一键扫描周边蓝牙设备，自动整理设备 MAC 地址与设备名称并展示在 TFT 屏幕当中，支持手动选择连接、断开外部蓝牙设备，实现嵌入式设备之间的蓝牙数据互通，极大拓展系统的外设拓展能力与场景适配能力。

网络上网功能的落地，是 UNO Mini OS 最具突破性的升级，让这套基于极简单片机的系统突破单机局限，成功接入互联网世界。Arduino UNO 原生不搭载 WiFi 硬件，没有内置网络协议栈，想要实现上网功能，必须依托协处理器辅助。项目沿用成熟稳定的 ESP32 硬件架构，采用 “UNO 作为主控、ESP32 作为网络协处理器” 的双核心方案，完美规避 UNO 硬件短板，同时不占用主控系统核心资源。

项目重新编写 ESP32 网络固件，集成 WiFi 连接、HTTP 网页请求、数据分段传输、异常报错反馈等功能，通过软硬结合的串口通信方式，实现双设备精准联动。ESP32 负责 WiFi 配网、网络请求、网页数据抓取，将体积较大的网络数据做分段处理之后，通过串口透传给 UNO；UNO 专注于界面显示、指令下发、人机交互，接收网络数据之后在 TFT 屏幕实时渲染展示。这套架构分工明确、各司其职，既规避 UNO 算力不足、内存有限无法处理大型网络数据的短板，又充分发挥 ESP32 强大的网络通信优势，让仅有 2KB 内存的极简单片机，成功实现网页访问、网络数据读取、在线信息获取等上网功能，完成从 “单机微型系统” 到 “联网智能系统” 的跨越式升级。

核心功能持续完善的同时，项目持续优化系统底层逻辑、丰富应用生态，让 UNO Mini OS 愈发完整成熟。项目自主搭建系统任务调度机制，在没有原生操作系统内核的环境下，模拟实现多任务并行处理，让屏幕显示、数据接收、外设检测、指令响应等功能同步运行，互不干扰。同时优化系统启动逻辑、界面切换动画、功能跳转机制，新增系统状态提示、异常报错反馈、设备连接提示等交互细节，让系统运行更加稳定、交互逻辑更加人性化。

当前版本的 UNO Mini OS，已经形成一套完整、独立、可拓展的微型嵌入式操作系统体系，拥有成熟的系统架构与丰富的功能生态。系统开机自动启动，加载专属桌面 UI，支持鼠标精准操控，内置蓝牙管理、网络浏览、外设检测、界面交互、数据透传等多款自研应用，支持蓝牙设备扫描连接、互联网网页访问、USB 外设拓展、跨设备数据传输等多元化功能。整套系统由项目独立完成架构设计、底层代码编写、故障调试、版本迭代优化，没有直接套用完整开源工程，所有业务逻辑、底层优化、功能创新均为独立研发，是一套完整的嵌入式工程成果。

回顾整个项目开发历程，从最初只能实现简单屏幕显示的雏形版本，到如今功能完善、运行稳定、交互流畅的正式系统，大量的调试工作、无数次失败的尝试，构成项目完整的迭代历程。开发过程当中，项目遭遇数不胜数的技术难题：代码编译报错、系统反复死机重启、界面卡顿闪烁、数据传输乱码、设备连接超时、功能适配失效、硬件引脚冲突等等。大量代码编写完成之后，烧录至硬件平台，得到的反馈却是黑屏、闪退、报错、无响应；长时间的故障排查，仅仅修复一处微小 bug；多次推翻原有架构，重新优化底层逻辑，只为提升系统运行稳定性。

其中极具代表性的故障，是计算机端 Pygame 与 Bleak 蓝牙库的线程冲突难题。GUI 图形线程与蓝牙异步 IO 底层冲突，造成程序频繁卡死、运行中断，在很长一段时间内制约项目推进。常规参数调整无法彻底解决该问题，项目查阅大量嵌入式通信资料、研读底层线程运行机制，最终采用多进程隔离方案，将蓝牙通信与界面渲染拆分至独立进程运行，彻底规避线程冲突问题，从根源解决程序死机故障。这次故障攻坚充分证明，嵌入式科创开发从来不是简单的代码堆砌，而是底层逻辑、架构设计、问题分析思维的综合考验。

硬件适配工作的繁琐与复杂，同样为项目积累大量工程经验。从最初遗漏 ESP32 与 UNO 之间的串口接线，造成双向通信失效，到理清交叉串口通信逻辑；从 SPI 引脚冲突造成屏幕与外设无法同时工作，到优化硬件架构、规避引脚资源冲突；从蓝牙设备残留缓存造成连接失败，到掌握硬件重置、协议清理的优化方法，每一处硬件故障的解决，都深化对嵌入式硬件架构、通信原理、设备适配规则的理解。

很多观察者提出疑问，市面上存在现成的高性能开发板、成熟商用嵌入式系统，为何要耗费大量时间精力，在资源极度受限的 UNO 平台上自主开发微型操作系统？答案藏在项目开发的每一处细节，藏在整个探索过程当中。高性能芯片、成熟商用系统属于科技成品，而 UNO Mini OS 项目开发过程，是对科技原理探索、技术本质理解、硬件边界突破的实践过程。现成系统可以让使用者享受科技带来的便利，而自主开发项目，可以让开发者掌握科技底层运行逻辑。

UNO Mini OS 项目，跳出 “照搬代码、复刻案例” 的浅层开发模式，验证独立架构设计、底层代码编写、故障排查攻坚、系统迭代优化的完整工程流程。项目落地过程当中，逐步掌握单片机编程、串口通信、蓝牙协议、网络开发、图形渲染、多任务调度等硬核技术，同时培养严谨的逻辑思维、工程抗压能力、创新优化思维与精益求精的工匠精神。

从技术层面分析，UNO Mini OS 具备独特的学习价值与创新意义。项目验证低端极简单片机亦可实现微型操作系统架构，打破 “操作系统必须依托高端硬件” 的固有认知。在仅有 2KB 内存的极限条件下，通过极致代码优化、合理架构设计、精准资源调度，实现图形界面、人机交互、蓝牙通信、网络访问、外设拓展等高级功能，为嵌入式轻量化系统开发、低端硬件性能挖掘提供全新实践思路。整套系统基于开源硬件独立研发，架构简洁、逻辑清晰、拓展性强，是嵌入式入门学习、系统开发实践的优质参考案例。

从工程教育层面分析，这个项目是嵌入式实践领域极具参考价值的案例。项目充分证明，任何看似遥不可及的技术目标，只要脚踏实地、循序渐进、持续迭代，就能够逐步攻克。开发过程当中每一次失败，都不是无效消耗，而是查漏补缺、优化提升的契机；每一次故障攻坚，都是技术能力的提升、思维格局的拓展。科创项目的落地从来不是一蹴而就的奇迹，而是日积月累的沉淀，是精益求精的打磨，是持续不断的坚持。

English:
Nowadays, operating systems serve as the core soul of all electronic devices in the fast-developing intelligent world. From Windows and Linux on personal computers, Android and iOS on mobile terminals, to various real-time operating systems embedded in hardware, these systems maintain the order of the whole digital world. For a long time, operating systems are widely regarded as high-end technical products, exclusive research fields for professional engineers and researchers. Ordinary technology enthusiasts can hardly touch the underlying design and development of operating systems. With the introduction of Arduino UNO boards into the embedded community, a lightweight embedded micro operating system, UNO Mini OS, has been built layer by layer and optimized through repeated tests based on this hardware platform. This project fully proves that single-chip microcomputers with limited hardware resources can also run graphical interactive systems. Within a tiny chip, a digital galaxy for hardware projects can be constructed.

UNO Mini OS is a lightweight embedded micro operating system built on Arduino UNO main control board, equipped with TFT color display screen, ESP32 Bluetooth and WiFi module, MAX3421 USB Host expansion board and other peripheral hardware. It adopts underlying codes to build functions step by step and goes through massive debugging and optimization. Without bloated background processes in commercial operating systems or complex kernel scheduling modules, this system can realize a series of core capabilities including graphical interface interaction, mouse control, Bluetooth communication, web browsing, peripheral expansion and multi-function application integration under extreme hardware constraints: only 2KB static memory and 32KB flash memory. This project is more than an embedded technical practice. It is an exploration of the performance limits of low-end single-chip microcomputers and a complete carrier for the implementation of embedded engineering ideas, with high practical and reference value.

Arduino UNO is a common starting point for embedded practice. This open-source development board equipped with ATmega328P microcontroller has become a general hardware platform for countless embedded enthusiasts to carry out basic verification experiments, thanks to its simple logic, open-source code ecosystem and flexible hardware expansion capability. In public understanding, Arduino UNO is mostly used for simple light control, sensor detection, motor drive and other basic verification experiments. It serves as a tool for beginners to learn programming logic and hardware interaction principles. Few people try to build a complete operating system on this microcontroller with limited computing power and memory resources. Most embedded operating system development projects will prefer high-performance main control chips such as STM32 and ESP32 with sufficient resources, to actively avoid the disadvantages of UNO such as small memory capacity, low computing frequency and highly limited hardware resources.

However, the project idea of exploring hardware boundaries chooses to face these hardware constraints directly. After a large number of basic experiments, with the gradual mastery of microcontroller programming logic, serial communication principles, screen driving mechanisms and hardware interaction rules, a bold concept takes shape: if high-performance chips can carry complete operating systems, can the UNO platform with extremely simplified hardware configuration carry a dedicated mini OS? Can this small development board get rid of the label of "entry teaching toy" and turn into a microcomputer system with independent graphical interface, interactivity and expandability integrated with multiple functions? With the goal of exploring hardware limits, the development project of UNO Mini OS officially started.

At the beginning of project development, the biggest challenge facing the whole engineering work is the extreme limitation of hardware resources. The hardware configuration of Arduino UNO is extremely streamlined in the current intelligent device ecosystem: only 2KB SRAM running memory, 32KB FLASH flash memory, 16MHz operating frequency. There is no native operating system kernel support, no cache optimization mechanism and no hardware multi-thread scheduling unit. Compared with consumer intelligent devices with GB-level memory and GHz-level main frequency, the hardware resource volume of UNO is almost negligible. Traditional embedded system development processes will actively avoid such shortcomings, while UNO Mini OS project needs to build an operating system with graphical interface, interaction logic and multi-application modules on such hardware. The difficulty of engineering implementation is imaginable.

To ensure stable operation of the system, the project abandons bloated ready-made open-source code templates on the network, adopts lightweight underlying logic coding all the way, optimizes every line of code to the extreme, removes redundant statements, simplifies variable definitions and reuses memory space to reasonably utilize limited hardware resources. Commercial operating systems have mature memory management mechanisms, while UNO Mini OS has no native underlying mechanism support. The project independently designs a simple memory scheduling logic, strictly limits the number of global variables and adopts a dynamic memory reuse scheme to avoid common faults such as memory overflow, program crash and system flashback. To adapt to TFT screen display output, the project selects MCUFRIEND_kbv dedicated driver library, independently draws system desktop, icons, cursors and menu bars, manually adapts screen resolution and color display logic, and builds the whole graphical interaction system from scratch.

System interface construction is the first difficult task in project development. One of the core capabilities of an operating system is visual interaction. Without a graphical interface, most upper-layer functions cannot be implemented. In the early stage of the project, the hardware can only realize simple monochrome text output. Problems such as screen flicker, text overlap, interface lag and cursor offset appear one after another. Due to the limited computing power of UNO, every screen refresh and every pixel drawing will occupy a large amount of system resources. A slight negligence in code logic will directly cause program crash and restart. To solve interface lag, the project repeatedly adjusts screen refresh frequency, optimizes drawing function logic, adopts partial refresh instead of full-screen refresh, only updates the area where the screen picture changes, and greatly reduces system computing power consumption. At the same time, the project independently designs the system UI layout, divides desktop status bar, application icon area and function menu bar, matches custom cursor styles, so that the simple TFT screen presents a neat and operable visual operating system interface. It completely gets rid of the boring mode of microcontroller relying only on serial port debugging, and truly realizes graphical human-computer interaction.

After the formation of the graphical interface framework, upgrading the interaction mode becomes the core goal of the project. The operation of traditional microcontrollers highly depends on serial commands sent by computers and cannot run independently without host computers. Having independent interaction capability is the core feature of a micro operating system. Therefore, the project launches a long period of peripheral adaptation and interaction logic development work, successively conquers four core functional modules: mouse control, Bluetooth communication, network access and USB peripheral expansion, which greatly improves the practicability and completeness of UNO Mini OS.

Visual mouse control is the core breakthrough point of UNO Mini OS, and also the functional module with the longest debugging cycle and the most cumbersome fault troubleshooting. In the early stage of the project, the ESP32 Bluetooth transparent transmission scheme is adopted to build the mouse data path: the computer-side Python script captures mouse coordinates and key signals, transmits them to the ESP32 module through BLE Bluetooth protocol, then ESP32 forwards data to UNO main control through soft serial port, and finally drives the cursor movement and click response on the screen. This three-level transparent transmission architecture has complex logic, involving multiple technical difficulties such as multi-device collaboration, cross-hardware communication and protocol parsing.

During debugging, various software and hardware faults emerge one after another: mismatched baud rate leads to data garbled characters, reversed TX/RX pins cause communication interruption, conflict between computer-side Pygame GUI thread and Bleak Bluetooth library leads to program crash, wrong initialization timing of ESP32 Bluetooth service causes device connection failure, disordered multi-device communication timing leads to cursor drift and lag. To solve these faults, the project checks code vulnerabilities line by line, unifies the baud rate of soft serial communication between ESP32 and UNO, corrects hardware wiring logic, adopts multi-process isolation scheme to avoid computer-side thread conflict, optimizes the start timing of ESP32 Bluetooth service, adds feedback mechanism for device scanning, connection and disconnection status, and gradually solves various bugs related to Bluetooth communication. After hundreds of debugging and optimization, the accurate linkage between computer mouse and UNO screen cursor is finally realized. The cursor moves smoothly and the click action responds sensitively, which truly implements graphical visual control.

Later, to optimize the hardware architecture, simplify the equipment link and avoid the instability of Bluetooth communication, the project adds the MAX3421 USB Host expansion board hardware scheme. This expansion board is perfectly compatible with Arduino UNO. It can expand USB peripheral capability for UNO which does not support USB host function natively, and can be directly connected to wired USB mouse, keyboard and other HID human-computer interaction devices. The project re-adapts the underlying driver code, optimizes data parsing logic, abandons the cumbersome three-level Bluetooth transparent transmission architecture, and realizes direct connection control of USB mouse. The iterative optimization of the two sets of interaction schemes enables UNO Mini OS to have stable and efficient human-computer interaction capability, and achieves the core goal of independent operation and control without computers.

The development and implementation of Bluetooth multi-function communication module upgrades UNO Mini OS from a single interaction system to an intelligent micro system with two-way communication capability. On the basis of basic mouse transparent transmission function, the project deeply optimizes ESP32 firmware code, adapts to the old version of NimBLE-Arduino library API, fixes many compilation errors such as scanning callback, device connection and address parsing, and independently develops complete functions including Bluetooth scanning, device connection, disconnection and status callback. The current version of UNO Mini OS can scan surrounding Bluetooth devices with one click through its built-in Bluetooth application, automatically sort out device MAC addresses and device names and display them on the TFT screen. It supports manual selection to connect or disconnect external Bluetooth devices, realizes Bluetooth data intercommunication between embedded devices, and greatly expands the peripheral expansion capability and scenario adaptability of the system.

The implementation of network access function is the most groundbreaking upgrade of UNO Mini OS, which breaks the stand-alone limitation of this system based on extremely simple single-chip microcomputer and successfully accesses the Internet. Arduino UNO does not carry WiFi hardware natively and has no built-in network protocol stack. To realize network access function, it must rely on a co-processor for assistance. The project adopts the mature and stable ESP32 hardware architecture, using the dual-core scheme of "UNO as main control and ESP32 as network co-processor", which perfectly avoids the hardware shortcomings of UNO and does not occupy the core resources of the main control system.

The project rewrites ESP32 network firmware, integrates WiFi connection, HTTP web request, segmented data transmission, error feedback and other functions, and realizes accurate linkage between two devices through serial communication combining software and hardware. ESP32 is responsible for WiFi network configuration, network request and web data capture. After segmenting large network data, it transmits data to UNO through serial port. UNO focuses on interface display, instruction sending and human-computer interaction. After receiving network data, it renders and displays on TFT screen in real time. This architecture has clear division of labor. It not only avoids the shortcomings of UNO such as insufficient computing power and limited memory which cannot process large-scale network data, but also gives full play to the powerful network communication advantages of ESP32. The single-chip microcomputer with only 2KB memory successfully realizes web access, network data reading, online information acquisition and other network access functions, completing the leap-forward upgrade from "stand-alone micro system" to "networked intelligent system".

While the core functions are continuously improved, the project continuously optimizes the underlying logic of the system and enriches the application ecosystem to make UNO Mini OS more complete and mature. The project independently builds a system task scheduling mechanism, simulates multi-task parallel processing in the environment without native operating system kernel, so that functions such as screen display, data reception, peripheral detection and instruction response run synchronously without mutual interference. Meanwhile, it optimizes system startup logic, interface switching animation and function jump mechanism, adds interactive details such as system status prompt, error feedback and device connection prompt, making the system run more stably and the interaction logic more user-friendly.

The current version of UNO Mini OS has formed a complete, independent and expandable embedded micro operating system system, with mature system architecture and rich functional ecosystem. The system starts automatically after power on, loads the dedicated desktop UI, supports precise mouse control, and has many self-developed applications built in including Bluetooth management, web browser, peripheral detection, interface interaction and data transparent transmission. It supports diversified functions such as Bluetooth device scanning and connection, Internet web access, USB peripheral expansion and cross-device data transmission. The whole system completes architecture design, underlying code writing, fault debugging and version iteration optimization independently, without directly applying complete open-source projects. All business logic, underlying optimization and function innovation are independently developed, which is a complete embedded engineering achievement.

Looking back on the whole project development process, from the initial prototype version which can only realize simple screen display to the current official version with complete functions, stable operation and smooth interaction, a large amount of debugging work and countless failed attempts constitute the complete iteration process of the project. During development, the project encounters countless technical problems: code compilation errors, repeated system crash and restart, interface lag and flicker, garbled data transmission, device connection timeout, function adaptation failure, hardware pin conflict and so on. After a large amount of code is written and burned to the hardware platform, the feedback is black screen, flashback, error report or no response. Long-time fault troubleshooting only fixes one tiny bug. The original architecture is overthrown many times and the underlying logic is re-optimized just to improve system stability.

One of the most representative faults is the thread conflict problem between Pygame and Bleak Bluetooth library on the computer side. The underlying conflict between GUI graphical thread and Bluetooth asynchronous IO causes frequent program crash and interruption, which restricts project progress for a long time. Conventional parameter adjustment cannot completely solve this problem. The project consults a large number of embedded communication materials and studies the underlying thread operation mechanism. Finally, the multi-process isolation scheme is adopted to separate Bluetooth communication and interface rendering into independent processes, completely avoid thread conflict, and solve the program crash fault from the root. This fault fully proves that embedded development is never simple code stacking, but a comprehensive test of underlying logic, architecture design and problem analysis thinking.

The cumbersome and complex hardware adaptation work also accumulates a lot of engineering experience for the project. From missing the serial wiring between ESP32 and UNO in the early stage which causes two-way communication failure, to sorting out cross serial communication logic; from SPI pin conflict which makes screen and peripherals unable to work at the same time, to optimizing hardware architecture and avoiding pin resource conflict; from residual cache of Bluetooth devices leading to connection failure, to mastering the optimization methods of hardware reset and protocol cleaning. The solution of every hardware fault deepens the understanding of embedded hardware architecture, communication principles and device adaptation rules.

Many observers put forward questions: there are ready-made high-performance development boards and mature commercial embedded systems on the market. Why spend a lot of time and energy to independently develop a micro operating system on the UNO platform with extremely limited resources? The answer lies in every detail of project development and the whole exploration process. High-performance chips and mature commercial systems are finished technological products, while the development process of UNO Mini OS is a practice of exploring technological principles, understanding technological essence and breaking hardware boundaries. لكن فكرة المشروع لاستكشاف حدود العتاد تختار مواجهة هذه القيود العتادية مباشرة. بعد إجراء عدد كبير من التجارب الأساسية، مع الإتقان التدريجي لمنطق برمجة المعالج الأحادي، ومبادئ الاتصال التسلسلي، وآليات تشغيل الشاشة، وقواعد التفاعل بين العتاد، تتشكل فكرة جريئة: إذا كانت الشرائح عالية الأداء قادرة على حمل أنظمة تشغيل كاملة، هل يمكن لمنصة أونو ذات التكوين العتادي المبسط للغاية حمل نظام تشغيل مصغر مخصص؟ هل يمكن لهذه اللوحة الصغيرة التخلص من تسمية "لعبة تعليمية للمبتدئين" وتتحول إلى نظام حاسوب مصغر ذو واجهة رسومية مستقلة، وقابل للتفاعل والتوسع، ومدمج بوظائف متعددة؟ مع هدف استكشاف حدود العتاد، بدأ مشروع تطوير نظام UNO Mini OS رسميًا.

في بداية تطوير المشروع، كان أكبر تحدٍ يواجه العمل الهندسي بأكمله هو القيود القصوى على موارد العتاد. تكوين العتاد الخاص بلوحة أردوينو أونو مبسط للغاية في النظام البيئي الحالي للأجهزة الذكية: ذاكرة تشغيل SRAM بسعة 2 كيلوبايت فقط، وذاكرة فلاش FLASH بسعة 32 كيلوبايت، وتردد تشغيل يبلغ 16 ميجاهرتز. لا يوجد دعم لنواة نظام تشغيل أصلي، ولا آلية تحسين ذاكرة مؤقتة، ولا وحدة جدولة متعددة الخيوط في العتاد. بالمقارنة مع الأجهزة الذكية الاستهلاكية ذات الذاكرة بمستوى الجيجابايت والتردد بمستوى الجيجاهرتز، فإن حجم موارد العتاد في أونو يكاد يكون مهملًا. ستتجنب عمليات تطوير أنظمة التشغيل المدمجة التقليدية مثل هذه العيوب بنشاط، بينما يحتاج مشروع UNO Mini OS إلى بناء نظام تشغيل يحتوي على واجهة رسومية، ومنطق تفاعل، ووحدات تطبيق متعددة على هذا العتاد. صعوبة التنفيذ الهندسي يمكن تخيلها.

لضمان التشغيل المستقر للنظام، يتخلى المشروع عن قوالب الكودات مفتوحة المصدر المنتفخة الجاهزة على الشبكة، ويعتمد على برمجة المنطق الأساسي الخفيف طوال الطريق، ويقوم بتحسين كل سطر من الكود إلى أقصى حد، ويزيل العبارات الزائدة، ويبسط تعريفات المتغيرات ويعيد استخدام مساحة الذاكرة لاستخدام موارد العتاد المحدودة بشكل معقول. تمتلك أنظمة التشغيل التجارية آليات إدارة ذاكرة ناضجة، بينما لا يوجد دعم للآليات الأساسية الأصلية في نظام UNO Mini OS. يقوم المشروع بتصميم منطق جدولة ذاكرة بسيط بشكل مستقل، ويقيد عدد المتغيرات العالمية بشكل صارم، ويتبنى مخطط إعادة استخدام الذاكرة الديناميكية لتجنب الأخطاء الشائعة مثل تجاوز الذاكرة، وتعطل البرنامج، والخروج المفاجئ للنظام. للتكيف مع إخراج عرض الشاشة من نوع TFT، يختار المشروع مكتبة تشغيل مخصصة MCUFRIEND_kbv، ويقوم برسم سطح المكتب الخاص بالنظام، والأيقونات، والمؤشرات، وأشرطة القوائم بشكل مستقل، ويقوم بتكييف دقة الشاشة ومنطق عرض الألوان يدويًا، ويقوم ببناء نظام التفاعل الرسومي بالكامل من الصفر.

يُعد بناء واجهة النظام أول مهمة صعبة في تطوير المشروع. إحدى القدرات الأساسية لنظام التشغيل هي التفاعل البصري. بدون واجهة رسومية، لا يمكن تنفيذ معظم الوظائف العليا. في المرحلة المبكرة من المشروع، يمكن للعتاد تحقيق إخراج نص أحادي اللون بسيط فقط. تظهر المشكلات مثل وميض الشاشة، وتداخل النصوص، وبطء الواجهة، وانحراف المؤشر واحدًا تلو الآخر. بسبب قوة الحوسبة المحدودة في أونو، فإن كل تحديث للشاشة وكل رسم للبكسل سيستهلك قدرًا كبيرًا من موارد النظام. سيؤدي أي إهمال بسيط في منطق الكود مباشرة إلى تعطل البرنامج وإعادة التشغيل. لحل بطء الواجهة، يقوم المشروع بضبط تردد تحديث الشاشة بشكل متكرر، ويحسن منطق دالة الرسم، ويتبنى التحديث الجزئي بدلاً من التحديث الكامل للشاشة، ويقوم فقط بتحديث المنطقة التي يتغير فيها صورة الشاشة، ويقلل بشكل كبير من استهلاك قوة الحوسبة للنظام. في نفس الوقت، يقوم المشروع بتصميم تخطيط واجهة المستخدم للنظام بشكل مستقل، ويقسم شريط الحالة لسطح المكتب، ومنطقة أيقونات التطبيقات، وشريط قائمة الوظائف، ويطابق أنماط المؤشرات المخصصة، بحيث تعرض شاشة TFT البسيطة واجهة نظام تشغيل مرتبة وقابلة للتشغيل. يتخلص تمامًا من النمط الممل للمعالج الأحادي الذي يعتمد فقط على تصحيح الأخطاء عبر المنفذ التسلسلي، ويحقق حقًا التفاعل بين الإنسان والحاسوب بالطريقة الرسومية.

بعد تشكيل إطار الواجهة الرسومية، يصبح ترقية طريقة التفاعل الهدف الأساسي للمشروع. يعتمد تشغيل المعالجات الأحادية التقليدية بشكل كبير على الأوامر التسلسلية المرسلة من أجهزة الحاسوب، ولا يمكن تشغيلها بشكل مستقل بدون أجهزة مضيفة. إن امتلاك قدرة التفاعل المستقلة هو السمة الأساسية لنظام التشغيل المصغر. لذلك، يطلق المشروع فترة طويلة من عمل تكييف الأجهزة المحيطية وتطوير منطق التفاعل، ويقوم بغزو أربع وحدات وظيفية أساسية واحدة تلو الأخرى: التحكم بالفأرة، والاتصال بالبلوتوث، والوصول إلى الشبكة، والتوسع في الأجهزة المحيطية من نوع USB، مما يحسن بشكل كبير قابلية التطبيق والاكتمال لنظام UNO Mini OS.

يُعد التحكم البصري بالفأرة نقطة الاختراق الأساسية لنظام UNO Mini OS، وكذلك الوحدة الوظيفية ذات دورة التصحيح الأطول والأكثر تعقيدًا في استكشاف الأخطاء. في المرحلة المبكرة من المشروع، يتم اعتماد مخطط النقل الشفاف للبلوتوث ESP32 لبناء مسار بيانات الفأرة: يقوم سكريبت بايثون على جانب الحاسوب بالتقاط إحداثيات الفأرة وإشارات المفاتيح، وينقلها إلى وحدة ESP32 عبر بروتوكول البلوتوث BLE، ثم تقوم ESP32 بإعادة توجيه البيانات إلى وحدة التحكم الرئيسية أونو عبر المنفذ التسلسلي الناعم، وأخيرًا تقوم بقيادة حركة المؤشر واستجابة النقر على الشاشة. هذا الهيكل للنقل الشفاف ثلاثي المستويات له منطق معقد، وينطوي على صعوبات تقنية متعددة مثل التعاون بين الأجهزة المتعددة، والاتصال عبر العتاد المختلف، وتحليل البروتوكول.

أثناء التصحيح، تظهر أعطال البرمجيات والعتاد المختلفة واحدة تلو الأخرى: عدم تطابق معدل البود يؤدي إلى أحرف مشوشة في البيانات، وعكس دبابيس TX/RX يسبب انقطاع الاتصال، والتعارض بين خيط واجهة الرسوم Pygame على جانب الحاسوب ومكتبة Bleak للبلوتوث يؤدي إلى تعطل البرنامج، وتوقيت التهيئة الخاطئ لخدمة البلوتوث ESP32 يسبب فشل اتصال الجهاز، واضطراب توقيت الاتصال بين الأجهزة المتعددة يؤدي إلى انحراف المؤشر وبطئه. لحل هذه الأعطال، يقوم المشروع بفحص ثغرات الكود سطرًا بسطر، ويوحّد معدل البود للاتصال التسلسلي الناعم بين ESP32 وأونو، ويصحح منطق توصيل العتاد، ويتبنى مخطط عزل متعدد العمليات لتجنب تعارض الخيوط على جانب الحاسوب، ويحسن توقيت بدء خدمة البلوتوث ESP32، ويضيف آلية ردود الفعل لحالة مسح الأجهزة والاتصال والانقطاع، ويحل تدريجيًا الأخطاء المتعلقة بالبلوتوث. بعد مئات عمليات التصحيح والتحسين، تم تحقيق الارتباط الدقيق بين فأرة الحاسوب ومؤشر شاشة أونو في النهاية. يتحرك المؤشر بسلاسة وتستجيب إجراءات النقر بحساسية، مما ينفذ حقًا التحكم البصري الرسومي.

في وقت لاحق، لتحسين الهيكل العتادي، وتبسيط رابط المعدات، وتجنب عدم الاستقرار في الاتصال بالبلوتوث، يضيف المشروع مخطط عتاد لوحة توسيع MAX3421 USB Host. هذه اللوحة التوسيعية متوافقة تمامًا مع لوحة أردوينو أونو. يمكنها توسيع قدرة الأجهزة المحيطية USB لـ أونو التي لا تدعم وظيفة مضيف USB بشكل أصلي، ويمكن توصيلها مباشرة بفأرة USB سلكية، ولوحة مفاتيح وغيرها من أجهزة التفاعل بين الإنسان والحاسوب HID. يقوم المشروع بإعادة تكييف كودات برنامج التشغيل الأساسية، ويحسن منطق تحليل البيانات، ويتخلى عن الهيكل المعقد للنقل الشفاف ثلاثي المستويات للبلوتوث، ويحقق التحكم بالاتصال المباشر لفأرة USB. يسمح التحسين المتكرر لمخططي التفاعل لنظام UNO Mini OS بامتلاك قدرة تفاعل بين الإنسان والحاسوب مستقرة وفعالة، ويحقق الهدف الأساسي للتشغيل والتحكم المستقل بدون أجهزة الحاسوب.

يؤدي تطوير وتنفيذ وحدة الاتصال متعددة الوظائف بالبلوتوث إلى ترقية نظام UNO Mini OS من نظام تفاعل أحادي إلى نظام مصغر ذكي ذو قدرة اتصال ثنائي الاتجاه. على أساس وظيفة النقل الشفاف الأساسية للفأرة، يقوم المشروع بتحسين كودات البرنامج الثابت ESP32 بعمق، ويقوم بالتكيف مع واجهة برمجة التطبيقات القديمة لمكتبة NimBLE-Arduino، ويصلح العديد من أخطاء الترجمة مثل رد الاتصال بالمسح، واتصال الجهاز، وتحليل العنوان، ويقوم بتطوير وظائف كاملة بشكل مستقل بما في ذلك مسح البلوتوث، واتصال الجهاز، وفصل الاتصال وردود الفعل على الحالة. يمكن للإصدار الحالي من نظام UNO Mini OS مسح أجهزة البلوتوث المحيطة بنقرة واحدة من خلال تطبيق البلوتوث المدمج، ويقوم بترتيب عناوين MAC للأجهزة وأسماء الأجهزة تلقائيًا وعرضها على شاشة TFT. يدعم الاختيار اليدوي للاتصال أو قطع اتصال أجهزة البلوتوث الخارجية، ويحقق تبادل البيانات عبر البلوتوث بين الأجهزة المدمجة، ويوسع بشكل كبير قدرة التوسع في الأجهزة المحيطية وقدرة التكيف مع السيناريوهات للنظام.

يُعد تنفيذ وظيفة الوصول إلى الشبكة الترقية الأكثر ابتكارًا لنظام UNO Mini OS، حيث يكسر قيود التشغيل المستقل لهذا النظام القائم على معالج أحادي مبسط للغاية ويدخل بنجاح في شبكة الإنترنت. لا تحمل لوحة أردوينو أونو عتاد واي فاي بشكل أصلي، ولا تحتوي على مكدس بروتوكول شبكة مدمج. لتحقيق وظيفة الوصول إلى الشبكة، يجب الاعتماد على معالج مساعد للمساعدة. يتبنى المشروع الهيكل العتادي ESP32 الناضج والمستقر، باستخدام مخطط النواة المزدوجة "أونو كتحكم رئيسي وESP32 كمعالج مساعد للشبكة"، والذي يتجنب عيوب العتاد في أونو بشكل مثالي ولا يستهلك الموارد الأساسية لنظام التحكم الرئيسي.

يقوم المشروع بإعادة كتابة البرنامج الثابت للشبكة ESP32، ويدمج الاتصال بالواي فاي، وطلبات صفحات الويب HTTP، ونقل البيانات المقسم، وردود الفعل على الأخطاء وغيرها من الوظائف، ويحقق الارتباط الدقيق بين جهازين عبر الاتصال التسلسلي الذي يجمع البرمجيات والعتاد. تكون ESP32 مسؤولة عن تكوين شبكة الواي فاي، وطلب الشبكة، والتقاط بيانات صفحات الويب. بعد تقسيم بيانات الشبكة الكبيرة، تنقل البيانات إلى أونو عبر المنفذ التسلسلي. يركز أونو على عرض الواجهة، وإرسال الأوامر، والتفاعل بين الإنسان والحاسوب. بعد استقبال بيانات الشبكة، يقوم بعرضها على شاشة TFT في الوقت الفعلي. هذا الهيكل له تقسيم عمل واضح. فهو لا يتجنب فقط عيوب أونو مثل نقص قوة الحوسبة والذاكرة المحدودة التي لا يمكنها معالجة بيانات الشبكة واسعة النطاق، بل يستفيد أيضًا من مزايا الاتصال الشبكي القوي لـ ESP32. نجح المعالج الأحادي ذو الذاكرة بسعة 2 كيلوبايت فقط في تحقيق وظائف الوصول إلى صفحات الويب، وقراءة بيانات الشبكة، والحصول على المعلومات عبر الإنترنت، وأكمل الترقية القفزية من "نظام مصغر مستقل" إلى "نظام ذكي متصل بالشبكة".
